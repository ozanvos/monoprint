# GPUI Fast migration benchmark — 2026-10-23

Monoprint Studio now selects published GPUI Kit **0.8.0** with its `gpui-fast`
feature and GPUI Fast **0.1.10**. The previous stack was GPUI Kit **0.7.1** and
GPUI Pre **0.3.8**. All eight measured workload/size combinations improved.
These results measure the combined dependency upgrade, not the isolated effect
of GPUI Fast versus GPUI Kit changes.

## Results

Apple M1 Max, arm64, macOS 27.0, Rust 1.98.1. Values are the median of 21
100-frame batch means from three independent processes, in **ms/frame**.

| Window | Workload | Before | After | CPU time reduction |
| --- | --- | ---: | ---: | ---: |
| 1440×900 | Unchanged frame | 4.368 | 1.331 | 69.5% |
| 1440×900 | Studio notification | 5.601 | 4.134 | 26.2% |
| 1440×900 | Inspector scroll | 4.807 | 4.073 | 15.3% |
| 1440×900 | Theme browser scroll | 8.093 | 3.773 | 53.4% |
| 1100×700 | Unchanged frame | 3.536 | 0.444 | 87.5% |
| 1100×700 | Studio notification | 3.542 | 2.036 | 42.5% |
| 1100×700 | Inspector scroll | 3.440 | 1.787 | 48.1% |
| 1100×700 | Theme browser scroll | 6.924 | 2.788 | 59.7% |

Raw data: [baseline](gpui-baseline-2026-10-23.json),
[GPUI Fast](gpui-fast-2026-10-23.json). Each records the source revision, dirty
state, lockfile hash, GPUI package versions and all batch samples. Both runs
used the same benchmark function and release profile (`lto = "thin"`).

## Method and limits

The existing headless native Studio harness creates the real editor, inspector,
preview and theme browser. After preview and editor initialization settles,
each workload discards one 100-frame warmup and records seven 100-frame batches.
Three fresh processes per stack give 16,800 measured frames per stack.

`Window::draw` and arena cleanup are timed. The unchanged workload draws an
unchanged view; it does not measure an idle application's CPU utilization.
The other workloads notify Studio, move its inspector scroll offset, or move
the virtual theme list. The draw path deliberately avoids the test helper's
forced full-window refresh, allowing retained rendering to work.

GPU presentation, VSync, screenshot readback, preview-worker rendering and
export time are excluded. Measurements were made on a shared development
machine; raw samples show scheduling variation. These batch statistics are not
per-frame tail-latency measurements or an end-to-end responsiveness guarantee.
Windows and Linux native behavior was not tested.

Reproduce the current stack from the repository root:

```sh
python3 apps/monoprint-gui/scripts/benchmark.py \
  --label gpui-kit-0.8.0-gpui-fast-0.1.10 --output /tmp/monoprint-gpui-fast.json
```

The baseline was captured before changing the manifest/lockfile, with the same
benchmark function and runner added to the 0.7.1 checkout. Result files record
that checkout's revision and lock hash; the benchmark code was uncommitted.

## Compatibility and verification

- GPUI Kit's supported feature selects Fast across its exported core, platform,
  Base, Component and assets. Kit still declares GPUI Pre dependencies internally;
  their presence in the lockfile does not select the application's backend.
- The popup patch was ported to `gpui-component` 0.8.0. Only `src/popover.rs`
  differs from the published component source.
- The App Store exclusions were ported from `gpui-pre-macos` to
  `gpui-fast-macos` 0.1.10. Only its feature manifests and `src/window.rs` are
  patched. Release source receipts now include the new vendor directory.
- Application source needed one explicit `IntoElement` import to resolve the
  new backend's derive exports. The all-feature Clippy gate also exposed an
  existing redundant App Store path conversion; both path branches now use
  `PathBuf` before joining the data-directory path, preserving their behavior.
- Focused native checks passed at both window sizes: notification-driven redraw
  without forced refresh, material/syntax pixels, keyboard input, interaction
  and popup motion, canvas gestures/resizing, file handoffs and emoji/CJK fallback.
  One initial small-window shadow-pixel assertion failed; an immediate rerun
  passed at both sizes. That transient failure's root cause was not established.
- Initial 1440×900 Studio screenshots were visually compared. Pixel differences
  were confined to the theme thumbnail (mean channel difference below 0.0002 on
  a 0–255 scale).
- At benchmark capture, GUI unit tests: **35 passed, 2 failed, 2 ignored**. Both failures reach the
  unchanged `src/originals.rs:22` `original reading surface` panic. The ordinary
  native suite reaches the same Ordinal-theme preview panic on **both** the
  saved baseline binary and GPUI Fast, so the complete product suite is not green.
  Those renderer/theme-data failures were outside the dependency migration;
  see the subsequent main-integration results below.
- Python macOS/App Store release tests: **12 passed**. GUI formatting and
  `git diff --check` passed.
- Clippy passed with `--release --all-targets --all-features -- -D warnings`.
  Upstream vendored Cocoa deprecation warnings remain dependency diagnostics.
- Production `--release --features app-store` build passed, followed by the
  project's `verify_app_store_apis` scan of the compiled executable. This is a
  local binary check; distribution signing and App Store submission were not run.

## Main integration and installation verification

Before installing, integrated main's `0131015` theme-routing fix into the
migration (`45f8e2d`). The GUI unit suite now passes **37 tests**, with zero
failures and two ignored manual benchmarks. The ordinary native suite passes
all workflows at 1440×900. At 1100×700 it still stops at the existing popup
shadow-pixel assertion (`resting = 4`, expected absolute difference above 5),
including on retry. That small-window test limitation remains unresolved;
the earlier theme-renderer panic is fixed by main.

The focused backend suite passes on the combined source at both window sizes,
including popup motion and notification-driven redraws. The ordinary full-suite
small-window popup assertion remains unresolved.
